# SP2a-1: The Lit Tree. Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking. Execution: Claude implements inline (the user's standing choice: no Codex, no subagents).

**Goal:** A knowledge tree built from general-knowledge structure and lit by the person's approved claims. The person sees what the standin may answer, and at what depth, with `standin map`. `standin map refresh` places topics, seeds from background, and proposes lighting changes for review.

**Architecture:**
- **`schema`:** fact attrs gain `background`, and competence attrs gain an optional `basis` and `reasons`. New topic, edge and gap records, the `map` role (large) and the `map` actor.
- **`store`:** migration 5 adds `topics`, `topic_edges` and `gaps`, with their queries.
- **`compaction`:** extraction tags background facts, and competence candidates match by tree node instead of text search.
- **A new package, `@standin/knowledge`:**
  - pure code: the tree snapshot, lighting rules, `answerMode`, proposals, wording;
  - model tasks: placing and merging topics, seeding from background;
  - `refresh`, which runs them all.
- **The CLI:** `standin map` and `standin map refresh`.

**Tech Stack:** Node 24, TypeScript (strict), zod v4, vitest, `node:sqlite`.

**Spec:** `docs/specs/2026-10-07-knowledge-map.md` §2, §3 and §5 (SP2a-1's scope, per decision 28). Parents: the architecture spec §7, the model-routing spec, and the memory-core simplification spec.

## Global Constraints

- **Depth scale:** 0–4. A dark node has no depth.
- **Lighting sources** (spec §3.2):
  - **Claim:** an approved competence memory with no `basis` (from the person's words), at its depth, with no cap.
  - **Background seeding:** core topics at **2**, basis `predicted`.
  - **Upward:** parent `min(child − 1, 3)`, the maximum over children, basis `predicted`.
  - **Prerequisite:** `min(d − 1, 3)` per hop, transitive, basis `predicted`.
  - **Precedence:** `probed` is never overridden (no probes yet in SP2a-1). Otherwise the highest of the claim and the inferred values wins. Inference may raise a node above a claim, as a proposal.
- **Inheritance** (decision 31): a node without its own approved lighting takes the nearest ancestor's approved lighting, of any basis. A gap on a node applies to that node and its descendants, and the nearest gap or own lighting on the path upward wins.
- **Stated gaps** (decision 30): an approved negative memory whose topic node has a lit ancestor creates a gap with:
  - `level: 1`, `status: "kept"`, `source: "stated"`;
  - `claimNodeId` = that ancestor.

  These need no review.
- **Proposals** (spec §3.6):
  - A rule value higher than the node's approved depth (or any value where there is none) becomes a proposed competence memory:
    - `attrs: { domain: <node name>, depth, basis: "predicted", reasons }`;
    - superseding the node's approved competence memory, if any;
    - linked to the node, actor `map`, no source observations.
  - It is not proposed if a pending or rejected proposal for the same node and depth exists.
  - A pending proposal for the same node at a different depth is rejected (actor `map`, note "replaced by a newer estimate") first.
- **Wording** (decision 18):
  - 0 "{t} isn't something I know."
  - 1 "I've heard of {t} but haven't used it."
  - 2 "I've used {t} and can get things done with it."
  - 3 "I know {t} well."
  - 4 "{t} is one of my deep areas."
  - Gap note: "I'm fine with {sub} up to {level}, but not deeper."
- **Background tag** (decision 29): extraction sets `background: true` on a fact stating the person's degree program, school, or job role.
- **Competence matching** (memory-core simplification §4): a competence candidate resolves to its topic node.
  - **Same depth** as an approved or proposed competence memory on that node: a duplicate (corroborate).
  - **Different depth:** a new proposal superseding the approved one.
  - No text search, and no reconcile call.
- **`answerMode`:** effective depth 3–4 → `explain`, 2 → `brief`, 0–1, dark or unknown node → `decline`. It also reports `boundary: true` when the node or an ancestor has `boundaryTier: 3`.
- **Refresh** (decision 32): `standin map refresh` does the model work and proposes. `standin map` makes no model calls. After approving a competence, background or negative memory, `standin approve` prints "Run `standin map refresh` to update your knowledge tree."
- **`map` role:** tier large, zone private, purpose "Place topics in the knowledge tree, merge duplicates, and seed from background". Seeding asks for "the core topics a person with this background would have covered (about 5–10)".
- **Commits:** Mingxi is the author. Every commit ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **A claimed topic the `map` role merges into another node** ("RL" claimed at 3, merged into "reinforcement learning"). The claim's memory link moves to the surviving node, which shows lit at 3. No node references the deleted one. Tested in Tasks 2 and 7.
2. **A placement that would make a cycle** (X placed under its own descendant). The edge is refused, the topic stays unplaced, and refresh continues and reports it. Tested in Task 7.
3. **A `map` model failure mid-refresh.** Steps that finished stay applied. The failed step adds one warning, and nothing is half-written, since each step runs in one transaction. Tested in Task 7.
4. **A negative memory whose topic has no lit ancestor** (or isn't placed yet). No gap is created, and it stays a plain negative. Tested in Task 5.
5. **Refreshing twice in a row** proposes nothing new the second time. Rejecting a proposal, then refreshing, doesn't bring it back. A new claim at a different depth does. Tested in Task 6.
6. **A node the person deleted** (store-level `deletedAt`; the UI comes in SP2a-2). It is not re-added by a later placement or seeding, and is excluded from lighting. Tested in Task 2.

```ts
export const PlaceSchema = z.object({
  merges: z.array(z.object({ from: z.string(), into: z.string() })),
  placements: z.array(z.object({ topic: z.string(), parent: z.string(), parentDefinition: z.string().nullable(), definition: z.string() })),
});
export const SeedSchema = z.object({
  field: z.object({ name: z.string(), definition: z.string() }),
  core: z.array(z.object({ name: z.string(), definition: z.string() })),
});
export async function placeTopics(store: Store, model: LLM, personaName: string): Promise<{ placed: number; merged: number; refused: string[] }>;
export async function seedBackground(store: Store, model: LLM, personaName: string): Promise<{ seeded: string[] }>;   // one call per unseeded background fact
export interface RefreshReport { placed: number; merged: number; refused: string[]; seeded: string[]; gaps: number; proposed: number; replaced: number; warnings: string[] }
export async function refresh(o: { store: Store; models: Models; tracer: Tracer; personaName: string }): Promise<RefreshReport>;
```
- **Unplaced topics:** live topics with no `part_of` parent that are linked to an approved memory and aren't a seeded field root.
- **`placeTopics`:** sends the unplaced names plus the current tree outline (name, parent, definition) in one `map` call. Merges apply first, then placements, which create the parent topic if it's new. A cycle is refused and listed.
- **`seedBackground`:** for each approved fact with `attrs.background` and no topic carrying its `seedMemoryId`, it creates the field and core topics, adds `part_of` core → field with source `seeding`, and sets `seedMemoryId` on the core topics.
- **`refresh`:** runs inside `tracer.run("map-refresh")`, in this order: seed, place, `syncStatedGaps`, `computeLighting`, `proposeLighting`. Each model step is in try/catch: a failure adds a warning and the steps after it still run on whatever exists.
